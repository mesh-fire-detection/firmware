# Mesh Fire Detection firmware integration audit — October 4, 2026

Status: open findings and proposed validation work. This review covered the MFD
integration and selected upstream MQTT code, not all Meshtastic firmware.
Seven default/configuration host tests passed. No new full firmware build,
flashing, device configuration, or field trial was performed during this audit.
Existing hardware evidence remains in [MESH_FIRE_DETECTION.md](MESH_FIRE_DETECTION.md).
See the [project audit](../backend/docs/reviews/2026-10-04.md) for other repositories.

## FW-01 — P1: website presets conflict with provisioning defaults

**Inspected.** [MeshFireDefaults.h](src/mesh/MeshFireDefaults.h) disables radio
transmission until private-channel provisioning. Website base/sensor JSON presets
enable transmission without including private-channel configuration. They also
enable power saving and disable Bluetooth, while MFD guidance defers deep sleep
until sampling and delivery have been tested.

**Proposal:** reconcile the public preset workflow with the current tested stage.
Define an ordered provisioning checklist: channel configuration, matching radio
settings, backend registration, gateway credentials/ACLs, verification, then
transmission. Never publish a private channel key in presets, builds, or reports.
**Acceptance:** a clean node following the guide does not transmit prematurely;
upgrades preserve configured identity, keys, and settings; presets agree with the
documented sampling/sleep policy. Record decisions in the responsible specifications.

## FW-02 — P1: documented QoS does not match native publishing

**Inspected; actual gateway verification required.** [MQTT.cpp](src/mqtt/MQTT.cpp)
calls PubSubClient.publish. The inspected installed TBPubSubClient implementation
forms a QoS 0 publish header. Backend MQTT.md currently states QoS 1. A subscriber
requesting QoS 1 does not upgrade the publisher's delivery guarantee.

**Proposal:** document the actual transport path and guarantees; test the chosen
gateway's behavior through outages and subscriber restarts. Any buffering or
transport change is a proposal until approved. See BE-06 for subscriber identity.
**Acceptance:** packet capture or equivalent broker evidence establishes publish
QoS; outage tests establish what is buffered, replayed, or lost, with bounds on
delay and storage. Cover a proxy transport separately if one is selected.

## FW-03 — P2: research and implemented sensor baselines differ

**Inspected.** The current integration uses BME680/PMSA003I; maps planning assumes
SPS30/BME688. **Proposal:** distinguish the bench prototype, proposed field
hardware, and research alternatives. **Acceptance:** parts catalog, expected
metrics, power measurements, calibration records, and maps assumptions identify
the same selected baseline or explicitly identify the different alternatives.

## FW-04 — P1: complete hardware-to-alert delivery remains a launch dependency

**Validation recommendation.** Existing notes distinguish local BME680 readings
from unverified private-channel/gateway delivery. Keep that distinction explicit.
The Notecard versus native MQTT gateway decision remains open; this audit does
not select a transport or claim the cellular path is implemented.

Before relying on real alerts, capture evidence for sensor → LoRa → gateway →
broker → backend reading → alert → UI. Include duplicates in both arrival orders,
loss of connectivity, reconnect, stale measurements, device disable, low battery,
particle warm-up, gas-sensor calibration, and the installed modules' power budget.
Preserve identity and configuration; use operator-authorized hardware operations.

Store reproducible fixtures without secrets and record board/modules, build,
settings, time, expected observations, actual result, and limitations. Confirm
transport TLS on the chosen gateway before changing the documented interim endpoint.

## Release and public evidence

The website currently labels firmware MIT while this repository's LICENSE is
GPLv3 (WEB-06). Align public descriptions with shipped license/notice artifacts.
Keep firmware, website UF2/checksum, flasher manifest, and source revision aligned
for each release. Passing defaults tests does not establish field smoke-detection
performance, autonomous cellular delivery, or battery lifetime.
